Git 2 협업 흐름 · Fork · 실무 습관 (33쪽부터) · HTML을 GitHub와 Vercel로 배포

➕ 슬라이드에 없는 추가 내용 · ✅ WSL Ubuntu에서 실행해 확인한 내용

💡 한 줄 요약 — 새 일은 브랜치에서 하고 git push -u origin 브랜치명으로 올린 뒤 Pull Request로 합친다. 권한이 없는 저장소는 Fork 해서 내 복사본에 올리고 원본으로 PR을 보낸다. GitHub 저장소를 Vercel에 연결하면 HTML이 주소가 있는 웹 페이지가 된다.

Git 2. GitHub로 협업 (33쪽부터)

1. 이름 정리: master, main, origin

이름정체
master예전부터 쓰던 기본 브랜치 이름. 설정을 하지 않은 Git은 지금도 이 이름으로 만든다
mainGitHub가 새 저장소에 쓰는 기본 브랜치 이름. 이 수업은 main으로 통일한다
origin원격 저장소(GitHub) 주소에 붙인 별명. 브랜치가 아니다
origin main"origin이라는 원격 저장소의 main 브랜치". git push origin 브랜치명의 뒷부분

✅ init.defaultBranch 설정이 없는 상태에서 git init을 하니 "Using 'master' as the name for the initial branch"라는 안내와 함께 master가 만들어졌다. git branch -M main으로 이름을 main으로 바꿨다.

브랜치 만들기 세 가지

명령하는 일
git branch 브랜치명만들기만 한다. 이동하지 않는다
git checkout -b 브랜치명만들고 전환 (예전 명령)
git switch -c 브랜치명만들고 전환 (지금 명령)

-u (upstream)

✅ 짝을 정하지 않은 브랜치에서 git push만 치면 "fatal: The current branch feat1 has no upstream branch"가 나왔다. -u로 한 번 올린 뒤에는 git push만으로 올라갔다. 짝은 브랜치마다 따로다. 새 브랜치 feat2에서는 다시 같은 오류가 났다. (바로잡기 B-1)

2. 협업의 기본 순서

모두가 main에 직접 push 하면 확인 없이 반영되어 main이 수시로 깨진다. 그래서 브랜치에서 작업하고 Pull Request로 합친다.

git switch -c readme-usage
nano README.md
git commit -am "사용법에 count.sh 추가"
git push -u origin readme-usage
# GitHub: Compare & pull request → 제목과 설명 → Create pull request → 리뷰 → Merge
git switch main
git pull                          # 병합된 내용을 받는다
git branch -d readme-usage        # 다 쓴 브랜치 삭제
  • Pull Request(PR)는 Git 명령이 아니라 GitHub의 기능이다. "내 브랜치를 base 브랜치에 합쳐 달라"는 요청이자 리뷰 자리
  • PR을 만들 때 base(합쳐질 브랜치)와 compare(내 브랜치)의 방향을 확인한다
  • 설명에는 무엇을, 왜, 어떻게 확인했는지를 적는다
  • 수정 요청을 받으면 PR을 새로 만들지 않는다. 같은 브랜치에서 고쳐 commit, push 하면 PR에 자동으로 추가된다
  • Issue에 할 일을 적고, PR 설명에 Closes #3을 적으면 병합될 때 Issue 3번이 닫힌다

PR에 충돌이 표시될 때

git switch main && git pull
git switch readme-usage
git merge main                 # 여기서 CONFLICT → 파일을 열어 표시 세 줄을 지우고 정리
git add README.md && git commit -m "main 과 충돌 해결"
git push                       # PR의 충돌 표시가 사라진다

Merge 버튼의 세 가지 방식

방식남는 이력
Create a merge commit (기본)가지 모양과 커밋이 그대로 남는다. 이 수업은 이것을 쓴다
Squash and merge여러 커밋을 하나로 뭉쳐 올린다
Rebase and merge커밋을 한 줄로 옮겨 붙인다

3. Fork로 남의 저장소에 기여하기

방식언제
Collaborator 초대팀 프로젝트. 초대받은 사람은 그 저장소에 직접 push 할 수 있다
Forkpush 권한이 없는 저장소에 기여할 때. 내 계정으로 복사해 와서 거기서 작업한다

수업에서 한 순서

  1. 강사 저장소 주소에서 Fork
  2. 내 GitHub에 생긴 fork 저장소를 clone
  3. 브랜치를 만든다
  4. 커밋하고 내 fork로 push
  5. 원본(강사) 저장소로 PR을 보낸다. base가 원본 저장소인지 확인
  6. 강사가 merge 하면 내 fork 페이지에서 Sync fork → Update branch
  7. git switch main && git pull — 내 컴퓨터까지 최신본으로 동기화 완료
git clone git@github.com:내계정/저장소이름.git
cd 저장소이름
git switch -c add-내이름
mkdir -p students && nano students/내이름.md
git add students && git commit -m "자기소개 추가 (내이름)"
git push -u origin add-내이름
# GitHub: PR 보내기 → 강사가 merge → 내 fork에서 Sync fork → Update branch
git switch main && git pull

6번을 건너뛰고 7번만 하면 받을 것이 없다. ✅ 원본에만 새 커밋이 있는 상태에서 git pull을 하니 "Already up to date."가 나왔다. origin은 원본이 아니라 내 fork를 가리키기 때문이다.

저장소에 올리면 안 되는 것

  • 비밀 키를 올렸다면 파일을 지우는 것으로 끝나지 않는다. 이력에 남으므로 그 키를 폐기하고 새로 발급받는 것이 먼저다

7. 🔍 슬라이드 바로잡기

슬라이드에서 틀렸거나 지금 환경과 다른 부분을 모았습니다. 슬라이드와 이 표가 다르면 이 표를 기준으로 보세요.

#슬라이드 내용바로잡기
B-1"-u 는 처음 한 번만 붙인다. 다음부터는 git push 만 치면 된다""처음 한 번"은 브랜치마다 한 번이다. ✅ 새 브랜치에서 git push만 치면 "has no upstream branch" 오류가 났다.
B-2슬라이드에 master가 없다오래된 저장소와 인터넷 자료에는 master가 많다. ✅ 설정 없는 Git은 지금도 master로 만든다. git branch -M main으로 바꾼다. 내 브랜치가 master인데 git push origin main을 치면 "src refspec main does not match any"가 난다.
B-3병합 뒤 정리: git branch -d 브랜치Squash and merge로 합친 경우에는 지워지지 않는다. ✅ "error: the branch 'sq' is not fully merged"가 나왔다. 내용이 main에 들어간 것을 확인했으면 git branch -D 브랜치(대문자)로 지운다.
B-4Fork 그림: git remote add upstream …, git pull upstream main수업에서는 이 명령 대신 GitHub의 Sync fork 버튼을 썼다. 둘 다 된다. ✅ 명령으로 하면 git pull upstream main 뒤 git push까지 해야 내 fork도 맞춰진다(pull 직후 상태는 ahead 3이었다).
B-5"공개 저장소면 수 분 안에 자동 수집되어 악용된다", "수백만 원이 나온 사례도 있다"자료를 만들 때 출처를 붙이지 않았고 직접 확인한 수치가 아니다. "공개 저장소에 올린 키는 노출된 것으로 보고 바로 폐기한다"가 근거 없이도 말할 수 있는 범위다.
B-6배포(Vercel)가 슬라이드에 없다수업에서 한 순서를 5장에 적었다. Vercel 화면의 버튼 이름은 직접 눌러 확인하지 않았다. 화면과 다르면 화면을 따른다.
B-7GitHub·Vercel 화면 순서 전반 (Fork, Sync fork, Compare & pull request, Collaborators)WSL에서 확인한 것은 Git 명령뿐이다. 웹 화면은 확인하지 않았다.

8. ➕ 더 알아보기 (슬라이드에 없음)

8-1. 대시보드에 API 키를 넣었다면

공공데이터포털의 API 인증키를 HTML(JavaScript)에 적어 공개 저장소에 올리면 4장의 "올리면 안 되는 것"에 해당한다. 저장소를 비공개로 해도 배포된 페이지의 소스 보기에서 그대로 보인다. 받은 데이터 파일(CSV·JSON)을 HTML에 넣는 방식이면 이 문제는 없다. 내 index.html에서 키 문자열을 찾아본다.

grep -n -i "servicekey\|apikey\|api_key" index.html

8-2. 고친 것을 다시 배포하기

Vercel은 연결한 저장소의 main에 새 커밋이 올라오면 다시 배포한다. 그래서 고칠 때는 배포 화면이 아니라 저장소를 고친다.

git clone git@github.com:내계정/my-dashboard.git
cd my-dashboard
(index.html 수정)
git add index.html && git commit -m "fix: 제목 수정" && git push

이 수업의 강의 자료실도 같은 방식(저장소에 push → Vercel이 배포)으로 운영된다.

8-3. fork를 명령으로 맞추기

git remote add upstream https://github.com/강사계정/저장소이름.git   # 처음 한 번
git switch main
git pull upstream main      # 원본의 최신 내용을 내 컴퓨터로
git push                    # 내 fork(origin)에도 올린다
git remote -v               # origin = 내 fork, upstream = 원본

✅ 연습용 저장소 셋(원본, fork, 내 컴퓨터)으로 위 순서를 실행해 원본의 새 파일이 들어오는 것을 확인했다.

8-4. 지금 브랜치의 짝 확인

git branch -vv        # [origin/feat1] 처럼 짝이 대괄호로 나온다. 없으면 아직 -u 를 안 한 것
