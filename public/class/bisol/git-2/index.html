1. 되돌리기

상황명령되돌아가는 곳
파일을 잘못 고쳤다 (add 전)git restore 파일마지막 커밋의 내용으로. 고치던 내용은 사라진다
잘못 담았다 (add 후)git restore --staged 파일스테이징에서 꺼낸다. 고친 내용은 그대로
방금 커밋의 메시지가 틀렸다git commit --amend -m "새 메시지"직전 커밋을 고쳐 쓴다
예전 커밋을 취소하고 싶다git revert 커밋반대로 고치는 새 커밋을 만든다

amend, revert, reset

amendrevertreset
하는 일직전 커밋을 고쳐 쓴다취소하는 커밋을 새로 만든다커밋을 없던 일로 한다
이력바뀐다 (해시가 달라진다)그대로 남는다바뀐다
언제아직 올리지 않은 내 커밋이미 남과 공유한 커밋아직 올리지 않은 내 커밋
git reset --soft HEAD~1    # 커밋만 취소. 담긴 채로 남는다 (HEAD~1 = 한 커밋 전)
git reset HEAD~1           # 커밋과 add 취소. 고친 내용은 남는다
git reset --hard HEAD~1    # 전부 취소. 고친 내용도 사라진다
git reflog                 # HEAD가 지나온 자리. reset으로 사라진 커밋의 해시를 여기서 찾는다
git reset --hard 해시      # 그 커밋으로 되돌아간다

2. .gitignore

데이터셋, 로그, 모델 파일은 Git에 넣지 않는다. 프로젝트 폴더에 .gitignore 파일을 만들어 제외할 것을 적는다.

dataset/
*.log
*.pt
적는 것제외되는 것이유
dataset/ data/이미지, 영상 데이터수 GB. 저장소가 무거워진다
*.pt *.pth *.onnx모델 가중치파일 하나가 수백 MB
*.log runs/학습 로그, 결과 폴더실행할 때마다 바뀐다

.envAPI 키, 비밀번호올리면 유출이다
  • .gitignore 파일 자체는 커밋한다. 그래야 동료의 컴퓨터에서도 같은 규칙이 적용된다
  • 이미 커밋된 파일은 .gitignore에 적어도 계속 추적된다. git rm --cached -r dataset으로 추적에서 뺀다

3. 브랜치

브랜치 = 하던 것을 건드리지 않고 갈라서 작업하는 가지. 폴더 복사가 아니라 커밋을 가리키는 이름표 하나가 더 생기는 것이라 순식간에 만들어진다.

명령하는 일
git branch브랜치 목록. *가 현재 위치
git branch 이름브랜치를 만들기만 한다
git switch 이름그 브랜치로 이동한다. 폴더에 보이는 파일도 그 브랜치의 것으로 바뀐다
git switch -c 이름만들고 바로 이동한다 (가장 자주 쓴다)
git branch -d 이름병합이 끝난 브랜치를 지운다

git checkout과 git switch

하고 싶은 일예전 명령지금 명령
브랜치로 이동git checkout 이름git switch 이름
만들고 이동git checkout -b 이름git switch -c 이름
파일을 마지막 커밋 내용으로git checkout 파일git restore 파일

✅ git checkout -b dev, git checkout dev, git switch dev 모두 같은 "Switched to …"가 나왔다. checkout은 브랜치 이동과 파일 되돌리기를 한 명령으로 하던 것이고, 그 둘이 switch와 restore로 나뉘었다. 인터넷 자료에는 checkout이 아직 많다.

병합

git switch main        # 합쳐질 쪽으로 먼저 이동한다
git merge report       # report의 커밋을 main에 합친다
git branch -d report   # 끝난 브랜치는 지운다
git log --oneline --graph --all   # 갈라졌다 합쳐진 모양 보기
상황결과
가지를 친 뒤 main이 그대로였다Fast-forward. 새 커밋 없이 main 이름표만 앞으로 옮긴다
양쪽 다 새 커밋이 있다병합 커밋이 하나 생긴다 (Merge made by the 'ort' strategy.)
fast-forward가 되는데도 병합 커밋을 남기고 싶다git merge --no-ff 이름

rebase(가지의 출발점을 옮겨 한 줄로 만들기)와 cherry-pick(커밋 하나만 골라 가져오기)도 소개했다. 이 과정에서는 merge로 통일한다.

main → dev → 개인 브랜치

git switch -c dev          # main에서 dev를 만든다
git switch -c lsc          # dev에서 내 브랜치를 만든다
(작업, add, commit)
git switch dev
git merge lsc              # 내 작업을 dev에 합친다
git switch main
git merge dev              # 확인이 끝난 dev를 main에 합친다

✅ 위 순서를 그대로 실행했다. 첫 개인 브랜치는 Fast-forward로, 두 번째 개인 브랜치는 병합 커밋으로 dev에 들어갔고, git merge dev는 Fast-forward였다.

4. 충돌

두 브랜치가 같은 파일의 같은 줄을 서로 다르게 고쳤을 때 난다. 오류가 아니라 Git이 "어느 쪽으로 할까요"라고 묻는 것이다.

git merge title
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.

해결 네 단계

nano README.md        # 1. 파일 열기
                      # 2. 남길 내용만 남기고 표시 세 줄을 지운다
git add README.md     # 3. 해결했다고 알린다
git commit -m "제목 충돌 해결"   # 4. 병합을 마무리한다

git merge --abort     # 겁나면: 병합을 없던 일로 하고 처음부터

VS Code에서는 표시 위에 "현재 변경 사항 수락"(내 브랜치), "수신 변경 사항 수락"(가져오는 브랜치), "두 변경 사항 모두 수락" 버튼이 나온다.

두 브랜치가 한 일결과
서로 다른 파일을 고쳤다충돌 없음
같은 파일의 서로 다른 줄을 고쳤다충돌 없음
같은 파일의 같은 줄을 다르게 고쳤다충돌. 사람이 정한다
한쪽은 고치고 다른 쪽은 그 파일을 지웠다충돌

줄이는 습관: 작게 자주 커밋하고 자주 합친다 · 시작하기 전에 최신 내용을 받는다 · 한 브랜치에서는 한 가지 일만 한다.

5. stash, tag

git stash          # 고치던 내용을 커밋하지 않고 잠깐 치워 둔다. 폴더가 깨끗해진다
git stash pop      # 다시 꺼낸다
git tag v0.1       # 중요한 커밋에 이름 붙이기 (제출한 버전, 발표한 버전)

브랜치를 옮기려는데 "Your local changes would be overwritten"이 나오면 커밋하거나 git stash 한 뒤 옮긴다.

9. 받아 오기: clone, fetch, pull

명령하는 일
git clone 주소원격 저장소를 통째로 받는다. 폴더 만들기, 이력 전체 받기, origin 등록까지 해 준다
git fetch새 커밋을 받아 오기만 한다. 내 파일은 그대로
git pullfetch + merge. 내 브랜치와 폴더의 파일까지 바뀐다
  • origin/main = 마지막으로 원격과 통신했을 때의 원격 main 위치. fetch나 pull을 해야 새로 고쳐진다
  • git status의 ahead 1 = 올리지 않은 내 커밋이 1개 → push / behind 1 = 받지 않은 커밋이 1개 → pull
  • 작업을 시작하기 전에 git pull부터 한다
git config --global pull.rebase false   # 처음 한 번: pull 할 때 병합(merge) 방식으로 합친다

10. push가 거절될 때

 ! [rejected]        main -> main (fetch first)
hint: Updates were rejected because the remote contains work that you do not have locally.

거절은 동료의 커밋을 덮어쓰지 않도록 막아 준 것이다. git push --force로 밀어 넣지 않는다. 동료가 올린 커밋이 사라진다.

혼자 쓸 때의 하루, 태그 올리기

git pull                        # 시작할 때
(수정 · add · commit 을 여러 번)
git push                        # 끝낼 때

git tag -a v1.0 -m "중간 발표 제출"
git push origin v1.0            # 태그는 따로 올려야 한다

13. 🔍 슬라이드 바로잡기

슬라이드에서 틀렸거나 지금 환경과 다른 부분을 모았습니다. 슬라이드와 이 표가 다르면 이 표를 기준으로 보세요.

#슬라이드 내용바로잡기
B-1"git checkout 이름은 git switch 이름과 같다"이름이 브랜치일 때만 같다. ✅ git checkout README.md처럼 파일 이름을 주면 묻지 않고 고치던 내용을 지웠다. 같은 것을 git switch README.md로 하면 "invalid reference" 오류가 나고 내용은 남았다. switch가 더 안전하다.
B-2브랜치 이름: "test, new, 내이름 같은 이름은 일주일 뒤에 아무도 모른다"수업에서는 개인 이름 브랜치(lsc, a, b …)를 썼다. 연습이나 "한 사람이 한 가지를 맡는" 작은 팀에서는 문제없다. 한 사람이 여러 일을 하게 되면 feature/label-report처럼 일의 이름으로 짓는다. 슬라이드의 단정이 지나쳤다.
B-3슬라이드에 dev 브랜치가 없다슬라이드는 "작업 브랜치 → main"만 다룬다. 수업에서 한 "개인 브랜치 → dev → main"은 3장에 따로 적었다.
B-4reflog = "사라진 커밋 되찾기"빠진 것 둘. 커밋한 적 없는 내용(reset --hard나 restore로 지운 고치던 줄)은 reflog에 없어 되찾지 못한다. 그리고 reflog는 그 컴퓨터에만 있다. ✅ clone 받은 저장소의 reflog에는 clone 이후의 기록 두 줄만 있었다.
B-5충돌 퀴즈 5번: "git diff 로 <<<< 를 찾는다"더 확실한 방법이 있다. ✅ git diff --check가 "leftover conflict marker"라고 줄 번호까지 알려 줬다. 그리고 ✅ 표시 줄을 지우지 않고 add, commit 해도 Git은 막지 않았다. 확인은 사람이 해야 한다.
B-6Git 2: "어제는 내 컴퓨터 안에서만 했다", "어제의 저장소"Git 1 뒷부분과 Git 2를 같은 날 했다. "어제"가 아니라 "앞에서"가 맞다.
B-7GitHub 화면 그림과 메뉴 이름(New repository, SSH and GPG keys, Collaborators)그림은 단순하게 그린 것이고, 자료를 만들 때 GitHub 화면에서 직접 눌러 확인하지는 않았다. 메뉴 위치가 다르면 실제 화면을 따른다.

14. ➕ 더 알아보기 (슬라이드에 없음)

14-1. 어느 브랜치가 이미 합쳐졌나

git branch --merged dev       # dev에 이미 합쳐진 브랜치 (지워도 된다)
git branch --no-merged main   # main에 아직 안 합쳐진 브랜치

✅ 개인 브랜치 둘을 dev에 합친 뒤 --merged dev에는 둘 다 나왔고, --no-merged main에는 dev와 개인 브랜치가 나왔다.

14-2. dev와 개인 브랜치를 GitHub에 올리고 받기

git push -u origin dev        # 브랜치마다 처음 한 번은 -u
git branch -a                 # remotes/origin/dev 처럼 원격의 브랜치까지 본다
git switch dev                # 받은 쪽: 원격에만 있는 브랜치도 이름만 치면 만들어져 따라간다

✅ clone 받은 저장소에는 처음에 main만 있었고, git switch dev를 치자 "branch 'dev' set up to track 'origin/dev'"가 나왔다. (GitHub 대신 같은 컴퓨터 안의 연습용 원격 저장소로 확인했다.)

14-3. 표시 줄이 남았는지 커밋 전에 확인

git diff --check              # leftover conflict marker 가 나오면 아직 남은 것

14-4. WSL과 Windows의 SSH 키는 따로다

WSL에서 만든 키는 WSL의 ~/.ssh에 있다. Windows의 Git Bash나 VS Code(Windows 쪽)는 다른 홈 폴더를 쓰므로 그 키를 보지 못한다. 수업처럼 WSL 터미널에서 push 하면 문제없다.
